# Roadmap

Each phase ends in something runnable.

1. **Spec.** Formal grammar for loose syntax. Exact syntax for tempering annotations, pause markers, and the shared-lock keyword. Precise enough to write a parser.
2. **Vertical slice.** Parser and type inferencer in Rust for a small subset (functions, numbers, strings, lists, control flow). Interpreter first, to prove the loose syntax feels right.
3. **Native backend.** Cranelift (decided). Generate native code for the subset. Benchmark against Python.
4. **Core differentiators.** Ownership inference, borrow checking, tempering, exception-to-Result error lowering. The hardest phase.
5. **Ecosystem.** Python typed bridge, Rust binary-level interop, unified package tool (one manifest, one lockfile), concurrency.

Concurrency and interop come last because they depend on everything beneath them.

Gut estimate: phases 1-3 (a prototype) about a quarter; a language trusted for real work, one to two years.

## Phase 5 (M6) plan

Nano, 2026-10-31. A real program drives M6, so the gaps it hits decide the order of stdlib work, not a list made in advance.

**Driver: fclone-lite**, a duplicate-file finder: walk a directory tree, group files by size, hash the candidates in groups of two or more, print each group of identical files. Oracle and speed baseline: `rusty_fclone` and a Python version of the same program, as CPython is for the corpus.

**Predicted gap order, a hypothesis to correct:** command-line arguments and `print` formatting; directory walking and reading files as bytes; `dict` and `set`; hashing. Record here what the program actually hits first, and reorder when it differs.

**Stdlib direction (unparked):** a Python-compatible surface over a Rust runtime. Anything shipped matches CPython or is on the [deviations list](grammar.md#deviations-from-python). I/O errors are tracked in `raises`, under an `OSError` base in the class hierarchy. No Rust-style API.

Not a card: relax this when the key is the unmodified loop variable (`for k in d: d[k] = ...`), which provably cannot change the dict's structure; revisit only if fclone-lite or the corpus shows the idiom matters. `for k in d.keys()` iterates the dict directly (no copy) and `x in d.keys()` is a lookup, in both backends, so growing the dict inside such a loop fails as CPython does. `sorted()` natively (a stable merge sort). The `True`-is-`1` key test runs in both backends (`dicts`); a `bool` stored in an `int`-keyed dict or set is stored as its int in both (Nano, 2026-10-31), a recorded deviation (`dict_bool_key`). The interpreter reads one fact from inference for this: whether a dict or set is `int`-keyed where it is made, stored to, passed or returned; a table also becomes int-keyed when it first stores an int. `build` refuses a bool stored as a key of an int-keyed table inside a generic function, since `run` may show it as `True` there (Nano, 2026-10-31; `dict_bool_key_generic` is in `NATIVE_GAPS`, and `corpus_matches_native` fails once it builds). Revisit when the interpreter gains specialization, or when generic stdlib code builds tables.

CPython's OpenSSL 3.5 picks its AVX2 assembly path on the measured CPU (Xeon with AVX2 and AVX-512, no SHA-NI) and runs about 1.2-1.5x faster; its plain assembly alone is about level with ours. The run is hash-bound, so native beats CPython there only if its hashing beats OpenSSL's; with the same hardware path as OpenSSL, parity is the expected outcome, not a proven ceiling. Revisit when a win is measured on SHA-capable hardware (x86 SHA-NI, ARMv8) or when hashing speed gates an app. rusty_fclone (xxh3, partial hashing, rayon) finds the same groups in 0.1s and is not a like-for-like baseline.
