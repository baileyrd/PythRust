# Loose Syntax Grammar (phase-2 subset)

Scope: the phase-2 subset only. Functions, numbers, strings, lists, control flow. Python-compatible wherever possible, so existing Python readers need no new model. Lexing and semantics follow CPython 3.13, the conformance oracle, unless listed under [Deviations from Python](#deviations-from-python).

Notation: EBNF. `A*` zero or more, `A+` one or more, `[A]` optional, `A | B` choice, `'x'` literal token.

## Lexical

- Indentation-sensitive, as in Python. The lexer emits `NEWLINE`, `INDENT`, `DEDENT`. Spaces only: a tab anywhere outside a string or comment is a lexical error.
- Line joining: implicit inside `()`, `[]` and `{}`, explicit with a trailing `\`, as in Python.
- Comments: `#` to end of line.
- Tokens: `NAME` (ASCII letters, digits, `_`; not starting with a digit), `INT`, `FLOAT`, `STRING`.
  - `INT`: decimal digits, `_` separators allowed. Ints are `i64`; arithmetic overflow is a runtime error, never a silent wrap. An `INT` literal above `i64::MAX` is a compile error, except `9223372036854775808` directly under unary `-`, which the parser folds to `i64::MIN`. Arbitrary precision may be added later as an opt-in type.
  - `FLOAT`: digits with `.` or exponent.
  - `STRING`: single or double quoted, with Python's `\` escapes except `\N{...}`. An unknown escape is an error. No string prefixes (`f`, `r`, `b`, `u`) or triple quotes yet; the lexer rejects them by name.
- Keywords: `def return if elif else while for in break continue pass and or not is True False None temper try except finally raise as import with pause` `as` is allowed only in a handler (`except Name as e`, `except (A, B) as e`) and after a `with` value (`with value as name:`); anywhere else it is an error saying so.
- Reserved for later (rejected by the lexer so programs stay forward-compatible): `assert class from lambda yield async await global nonlocal shared`. `match` is not reserved: it is a common Python name, and Python's own `match` is a soft keyword.

## Program

```ebnf
module      = (import_stmt)* (stmt)* ENDMARKER ;
import_stmt = 'import' NAME (',' NAME)* NEWLINE ;         # a standard (M6a) or local module, or a binding
stmt        = simple_stmt NEWLINE | compound_stmt ;
block       = NEWLINE INDENT stmt+ DEDENT ;
```

## Statements

```ebnf
simple_stmt = assign | ann_assign | aug_assign | return_stmt | raise_stmt | del_stmt
            | 'break' | 'continue' | 'pass' | expr_list ;

assign      = target_list '=' expr_list ;
ann_assign  = NAME ':' type '=' expr ;
aug_assign  = target ('+=' | '-=' | '*=' | '/=' | '//=' | '%=' | '**=') expr ;   # target must not be a tuple (checked after parsing)
return_stmt = 'return' [expr_list] ;
raise_stmt  = 'raise' expr ;                              # bare `raise` is later
del_stmt    = 'del' primary '[' expr ']' ;                # one subscript of a list or dict (D70)
target_list = target (',' target)* [','] ;                # more than one, or a trailing comma, unpacks
target      = NAME | postfix | '(' target_list ')' ;      # postfix must end in a subscript_op (checked after parsing)

compound_stmt = func_def | if_stmt | while_stmt | for_stmt | try_stmt | with_stmt ;

func_def    = ['temper'] 'def' NAME '(' [params] ')' ['->' type] [raises] ':' block ;
raises      = 'raises' NAME (',' NAME)* ;                # contextual: `raises` stays a name elsewhere
params      = param (',' param)* [','] ;
param       = [mode] NAME [':' type] ['=' expr] ;
mode        = 'mut' | 'owned' ;                         # contextual: a mode only before a NAME

if_stmt     = 'if' expr ':' block ('elif' expr ':' block)* ['else' ':' block] ;
while_stmt  = 'while' expr ':' block ['else' ':' block] ;
for_stmt    = 'for' target_list 'in' expr ':' block ['else' ':' block] ;
try_stmt    = 'try' ':' block ( handler+ ['finally' ':' block] | 'finally' ':' block ) ;  # `else` is later
handler     = 'except' classes ['as' NAME] ':' block ;
classes     = NAME | '(' NAME (',' NAME)* [','] ')' ;     # each NAME is a builtin exception class (checked by inference)
with_stmt   = 'with' with_item (',' with_item)* ':' block ;  # items nest left to right (D111); `with (a as x, ...)` is later (D113)
with_item   = expr ['as' NAME] ;                         # an executor, or a direct call of the builtin `open` (not a program's own `open`, D115), which alone may omit `as` (D109, D112)
```

### Notes

- **Imports (M6a, Nano 2026-10-31):** `import sys` brings in a standard module, a Python-compatible surface over the Rust runtime (`stdlib.rs`; [roadmap](roadmap.md#phase-5-m6-plan)). Imports come first in a module, so a module name is known wherever it is used: `sys.argv` is one name, a module variable is a global and a module function a builtin. Modules: `sys` (`sys.argv`, a `list[str]`); `hashlib` (below); `os` (`os.listdir(path='.')`, a `list[str]`; `os.path.join(a, *p)`; `os.path.isdir`, `isfile` and `islink`, `False` on any error; `os.path.getsize`, an `int`). `os.listdir` and `os.path.getsize` may raise an `OSError`, which `raises` tracks (D8) as any `raise` does: `str(e)` is CPython's `[Errno 2] No such file or directory: 'p'`, its `repr` CPython's `FileNotFoundError(2, 'No such file or directory')` (the exception holds `errno`, `strerror` and `filename`, though a program cannot read them yet), and the class is the subclass the error names. `os.listdir` takes its `path` by keyword too, as CPython names it; the other module functions take positional arguments only. The builtin `open(path, mode="r", encoding=None)` (M6a; text and writing #1171, D91) returns a file, not spellable in annotations. The mode is a string literal, one of `"r" "rt" "w" "wt" "a" "at" "rb" "wb" "ab"`; a file's type carries its kind (D99): a text reader or writer is CPython's `_io.TextIOWrapper`, `"rb"` its `_io.BufferedReader` and `"wb"`/`"ab"` its `_io.BufferedWriter`. Same-kind files share a variable (`"w"` then `"a"`); a reader and a writer do not (one fixed type per variable). A text reader has `read()` (the rest, a `str`), `readline()` (`""` at the end) and lines (keeping their `"\n"`) for `for line in f` and `list(f)`; no other consumer reads a file's lines yet (D100). A binary reader has `read()` (`bytes`). A text writer has `write(s)` (the code points written), a binary writer `write(b)` (the bytes written). Every file has `flush()` and `close()` (again does nothing, and it stays a value: printing it still works), and dropping its last reference closes it, as in CPython. Text is UTF-8 only (`encoding=` a UTF-8 spelling or `None`, D95), with CPython's newlines (D94); writes are buffered and flushed by `flush`, `close`, the last reference's drop and every program exit (D98). Reading a writer or writing a reader is a compile error (D92, D99). `with open(...) as f:` (#1374, D109-D114) closes the file on every way out of the block (its end, `return`, `break`, `continue`, an exception) but a fatal fault, as `try`/`finally` would, and `f` stays bound to the closed file; `as f` may be left out. The value must be the `open(...)` call itself; several items (`with open(a) as f, open(b, "w") as g:`) nest left to right and may mix in an executor. The file closed is the one the `with` opened, even if the block rebinds `f`. A writer's close may raise an `OSError`, tracked in `raises`. Invalid UTF-8 read as text raises `UnicodeDecodeError` (a `UnicodeError`, a `ValueError`) with CPython's message, tracked in `raises` (D93). `open`, and `read`, `readline`, a `for`, `write`, `flush` and a writer's `close` may raise an `OSError` (D96) (`[Errno 21] Is a directory: 'p'` for a directory, which Unix would open), tracked in `raises`; reading a closed file raises CPython's `ValueError: read of closed file`, and a path holding a NUL CPython's `ValueError: embedded null byte` (`character` on Windows), both untracked like the operator faults (D7). `bytes` (annotation `bytes`) supports `len`, `==` and `!=`, truthiness, `str()` and `print` (CPython's `repr`, `b'...'`), and storing in containers; it has no literals, indexing, iteration, ordering or hashing yet. A file compares by identity in CPython, so comparing one is a compile error. A file parameter the body reads, writes, flushes, iterates or closes (`f.read()`, `f.write(s)`, `for line in f`, `f.close()` on the parameter itself) needs `mut` (D2, D97). The rule is syntactic: a copy of the parameter is not followed, so `g = f; g.read()` is missed. Since no file type is spellable yet, only loose functions take files, so `mut` is inferred there and never demanded. `hashlib` (M6a) offers `hashlib.sha256(data).hexdigest()` of `bytes`, a `str`: the parser reads the call and its `.hexdigest()` as one, since the hash object is not a value yet, so `hashlib.sha256(data)` alone, or with another method, is an error saying so. SHA-256 is hand-written in the runtime (`pythrust-rt/src/sha256.rs`), which the interpreter compiles too. A module is not a value, its names cannot be assigned, and its name cannot be bound by a `def`, a parameter or `except ... as`. A standard module Pythrust lacks (`import json`) is "not supported yet" (D81). `from`, `import a.b` and `import a as b` come with post-M6 step 3's #1222 (D75, D84; [Modules](#notes) below). `pythrust run <file> [arg ...]` passes the arguments after the file, as `python3` does.
- **Rust bindings (M6b, Nano 2026-10-31; implemented for `check` and `build`):** `import name` also brings in a Rust binding that the project's [`pythrust.toml`](#manifest-pythrusttoml) names as `name = { path = "..." }` in `[rust]` (M6d; `--rust name=path` is gone). The manifest is the first `pythrust.toml` in the program's directory or above, read only when some module of the program imports a local module or a name that is neither standard nor local (D81, D125). The binding's stub `path/name.pyr` holds only `temper def` signatures whose bodies are `...`; `...` is a named error anywhere else ("stub bodies only; use pass" for a statement), and so is `mut` or `owned` on a stub parameter ("not supported in stubs yet"). A stub declares at least one function. Every stub parameter is annotated and has no default, every stub has a return annotation, each type is one in the list below (a result may also be `None`), and `raises` may list only `OSError` or `Exception`, which name the builtins whatever the program defines; a call to a stub raising a class the program redefines is an error. Calls check against stubs like any tempered function. Parameters are `read`; `int`, `float`, `bool`, `None`, `str`, `bytes` and `list[str]` cross, and `Result<T, io::Error>` is `raises OSError` ([research/rust-interop.md](research/rust-interop.md)). `run` of a program that imports a binding refuses ("run cannot call Rust bindings yet; use build"), since the interpreter cannot call Rust; `build` is the way to run it. It needs cargo with Rust 1.97 or later for the bindings and for building pythrust itself. A stub that disagrees with its Rust function fails the build, naming the stub. A panic in Rust ends the program as a fault at the call does ("Rust panic: message") and is never catchable. A binding is a Cargo package (of any name; the program calls it by the binding's name) and its own workspace. `pythrust lock` resolves every binding of `[rust]` into the project's `pythrust.lock`, which `build` needs and holds every crates.io version to ([research/package-tool.md](research/package-tool.md)); a binding's own `Cargo.lock` is ignored. To update dependencies, delete `pythrust.lock` and run `pythrust lock`.
- **Tasks (M6c, Nano 2026-11-01; `check`, `run` and `build`):** `import concurrent.futures` (the one dotted import; `import concurrent` alone is an error) gives `with concurrent.futures.ThreadPoolExecutor() as ex:`, one of the two `with` values (the other is `open(...)`, [Imports](#notes)). `ex.submit(f, *args)` runs `f` as a task and returns a future (`Future[T]`, not spellable yet); `fut.result()` returns what `f` returned, or raises what escaped it. `ex.map(f, xs)` runs `f` on each element of `xs`, read once when `map` is called, and returns its results in order (`Iterator[T]`), which a `for`, `list`, `sorted`, `set` or `in` takes once; a task's exception is raised by the step that takes its result and ends the results. `f` is the name of a `def` (not a Rust binding function, until an app needs one: Nano, 2026-11-02), its arguments checked as a call's, positional only; `map` passes one. Leaving the block waits for every task it started. `raises` (D8) counts what each task of a function may raise wherever that function takes a result. Executors, futures and `map`'s results stay in the function that made them: no parameter, result, global, exception or call argument (but `append` to a local list and `len`, `list`, `sorted`, `set`) holds one, only a local list may hold futures, an executor is named only by its `with`, which makes a fresh one, and used inside it, `map`'s results are bound only from `ex.map(...)` and used inside that executor's block (a use any binding of the name may reach from outside its block is an error), and there is no executor at module level. Futures and executors compare by identity in CPython, so comparing one is a compile error. `run` runs each task to completion at `submit`, with its own call depth from zero ([research/concurrency.md](research/concurrency.md#run-at-submit)). For the ownership checks (modes D2, aliasing D3/D4, shared arguments A5), each task is a call of its function where it is submitted, as `run` runs it, and `map` one such call per element; what escapes a task is raised where its result is taken, as `raises` counts it, never at the call; a function that uses tasks is checked like any other (step 3b). A program that uses tasks and meets a lowering gap, which would leave every function unchecked, is a compile error naming that gap (Nano, 2026-11-02). Between tasks (rule 4, [research/concurrency.md](research/concurrency.md#rule-4-in-full); `own/tasks.rs`): in each `with` block, the submitter from a task's call to the block's end, and each task, are parties, and two conflict when one changes or keeps a list (dict, set) the other touches, touching a value touching every list inside it; a call that may start several tasks (`map`, or a `submit` in a loop) is a party against itself, a nested executor's tasks count in the outer block, and a task's result counts as the arguments its function may return. Module values are told apart by the list variables a party's code and callees load; every list a parameter, a module value or an exception may be or hold counts as one list with the module's values, since a caller may pass one list as two arguments or a module list (conservative parameter aliasing, kept by Nano 2026-11-02; revisit when a real program is rejected), and an exception touched reaches all of them. No file reaches a task, as an argument or a module variable or default its code reads, nor inside an exception once any exception the program makes holds a file, and `map` runs no function that changes or keeps its parameter. Each is a compile error naming the shared value ("`xs` is read by a task until the `with` block ends").
- **Modules (post-M6 step 3, Nano 2026-11-03; `import a` done in #1220, the other forms planned in #1222):** a program may span several `.pyr` files ([research/modules.md](research/modules.md)). Modules are found from the project root, the `pythrust.toml` directory, else the main file's; `import a.b` is `<root>/a/b.pyr`, directories are namespace packages, and there is no search path (D75, D78). A name is a stdlib module (any name in CPython 3.13's `sys.stdlib_module_names`), else a local module, else a `[rust]` binding of the root manifest; a local module named like a stdlib module or like a binding is a named error (D75, D81). The forms are `import a`, `import a.b`, `from a import x` and `as`, for local and stdlib modules (D84); imports come first in each module. Top-level code runs once per module, depth-first in import order, as in CPython; a circular import, including one through the main file, is a compile error (D75, D83). `from a import x` binds a global holding the same object, and a missing `x` is a compile error; `__name__` is `"__main__"` in the main file and the dotted name elsewhere (D83). The whole module graph is analyzed and built as one program, keyed by qualified name (D76, D77). Only function-level tempering exists in any module (D108). As built in #1220: a module's file is `<root>/a.pyr`, spelled exactly as imported, case included (a file differing only in case is an error saying so), and a module file beside a directory of its name is an error naming both; `run`, `check` and `build` load the graph before any check. A module's names are qualified (`a.x`) for every later stage, so a diagnostic in another file names them so, while one in the module's own file names them as written there. When a module imports a local module, the manifest is read if there is one (D125), so a local module named like a binding is always an error, and a malformed manifest fails such a program; a program importing only standard modules never reads it. Diagnostics name a module's own names as written in its own file, and qualified (`a.f`) elsewhere (D127); an uncaught exception's message is the program's text, shown as raised by `run` and native code alike. Each module keeps its own lookup: a name it reads but does not bind is a builtin's (else undefined, a compile error), never a global of the main file, which may shadow that builtin for itself alone (D76); so are the exception classes its `except` and `raises` clauses name, and a module that rebinds one cannot name it there, as in one file. A call before the module's own `def` of a builtin's name runs finds the builtin, as in one file, and `raises` counts it so; a `def` that leads its file (after its `__name__`) runs before any code that could call it, and a binding's function is never a builtin. Every module has `__name__`, which an importer may read as `a.__name__`, and rebinding it is ordinary assignment (D83). A standard module's variables (`sys.argv`) are initialized once, by its first import, and every importer shares them. Fixtures in `examples/modules/`.
- **Pause (M6c, Nano 2026-11-02):** `pause <expr>` marks an expression that waits on a task; it covers the whole expression to its right, up to a comma that separates expressions (`pause f(x) if c else y` covers the conditional; `x, y = pause a.result(), b.result()` covers only the first), and changes nothing the program does. It starts an expression: inside another, wrap it in parentheses (`not (pause f.result())`, `[0] + (pause list(rs))`); a marker covering a parenthesized expression covers its parentheses. A pause point is `fut.result()`, each step of a `for` over `map`'s results (marked on the iterable: `for r in pause ex.map(f, xs):`), `list`, `sorted`, `set` or `in` on them (marked on that call or test: `pause list(ex.map(f, xs))`), and a call to a function that pauses. A function pauses when its body holds a pause point or an executor's `with`, whose end waits for its tasks; `submit` and `map` wait for nothing. Tempered code marks every pause point but the end of a `with` block ("`result()` waits on a task; tempered `f` marks it: write `pause` before it"), so tempered code may use executors; loose code may mark them and need not. Every `pause`, loose or tempered, covers a pause point ("nothing here can pause"), so `list(pause ex.map(f, xs))` is an error: the marker covers only `map`, which waits for nothing. `infer/pause.rs`; [research/concurrency.md](research/concurrency.md#the-rest-of-m6c-decided-nano-2026-11-02).
- `temper def f(...)` marks a function *tempered*: the compiler requires more to be written explicitly, and the meaning never changes (see [design.md](design.md#core-idea-tempering)). Only function-level tempering exists here; module- and project-level tempering come later (D108). The keyword is a prefix, not a decorator, so the compiler sees it without resolving names.
- Annotations are optional everywhere. Loose code infers them; they are hints, never required.
- Single-line bodies (`if x: y`) are not in phase 2. One way to write a block.
- Attribute assignment (`a.b = c`) waits for classes.
- `def` appears only at module top level. Nested functions bring closure capture, which waits for ownership (phase 4).
- Since M5 (A1), a `temper def` must annotate every parameter and its return completely (no bare `list`), and may call only tempered functions and builtins (D1, D5 below). Loose code may call it freely. The other tempered rules land with the rest of M5.
- Parameter modes (phase 4, D2, A4): `mut xs` says the function may change the list `xs` (or a list inside it) in place, `owned xs` that it may also keep it after returning (store it in another list, a global, or pass it to a function that does). `read` is the default and never written; writing it is an error that says to drop it. The compiler infers what each body does to its parameters and checks it against what is written: a tempered function's unwritten mode means `read`, so it must write each `mut`/`owned` its body needs; a loose function's unwritten mode is inferred, and only the modes it writes are checked. Writing more than the body needs is allowed, as over-declaring `raises` is. Returning a list parameter is not a mode (D3 covers it); holding it in an exception is `owned`, since the exception may outlive the call. Which modes a parameter may have depends on its type (A8, Nano 2026-10-29): a *heap type* is `str`, `list`, `dict` or `set` (M6; later objects), or a tuple or optional holding one; anything else (`int`, `float`, `bool`, `None`, `range`, a tuple or optional of them) is a *value type*, which is copied. `owned` is allowed on any heap type and required when the body keeps the parameter: for a string, or a tuple or optional holding one, that means returning it, storing it in another value or a global, or holding it in an exception; a list inside such a value keeps the list rules, and a list's elements are values of their own. `mut` is allowed only when the type's own operations reach a mutable heap value: a list, dict or set, or a tuple or optional holding one (`tuple[list[int], int]`, `list[int] | None`), whose container can change in place; rebinding a tuple element stays an error. On `str`, a scalar-only tuple or optional, or an exception, `mut` is an error that names what cannot change ("strings cannot change in place; remove `mut` from `s`"). An exception is an immutable heap value: `owned` when kept, including re-raising a parameter, and never `mut`, even one carrying a list (A6 rule 4), since no operation reaches the list (revisit if `e.args` lands). Either on a value type is an error ("ints are copied; remove `owned` from `n`"). The classification is on the language-level type (`infer::Type::holds_heap` and `reaches_mutable`), not on how a backend represents it, so unboxing tuples later changes no program's legality. A generic parameter may write either. Every function whose signature is concrete is checked, called or not; a generic function is checked through the instances its calls create. A program part of which the native backend cannot yet express has its modes checked once it can (the analysis is otherwise conservative and diagnoses nothing), except in a program containing a `temper def` or using tasks, where the gap is a compile error naming it (Nano, 2026-11-03). `check`, `run` and `build` apply the same check. Modes change no behavior: removing them leaves a passing program's output unchanged.
- Rejected by the parser, as CPython rejects them before running: `return` outside a function, `break`/`continue` outside a loop (a loop's `else` is outside it), duplicate parameter names, a parameter without a default after one with a default, a positional argument after a keyword argument, and a repeated keyword argument.
- Parameters: defaults are evaluated once, when `def` runs, as in Python. A call binds positional arguments first, then keyword arguments by name. An unknown name, a parameter bound twice, or a parameter left unbound is an error.
- Declared errors (phase 4, D8): `raises` lists the exceptions that may escape a function: builtin exception classes that nothing redefines. A class admits the classes derived from it (B4), so `raises ArithmeticError` covers a `ZeroDivisionError` and `raises Exception` covers any. A loose function without a clause infers its set from its body and its callees; a tempered function, or any function with a clause, has the set it declares, and its body may let nothing else escape. A tempered function without a clause declares that nothing escapes. Callers see the declared set, and listing more than escapes is allowed. What escapes: each `raise`, and `int(s)` / `float(s)` (`ValueError`) unless the argument is a number, `chr(n)` (`ValueError`) unless `n` is an int literal in range, `min`/`max` of an iterable (`ValueError`), `s.index`/`s.rindex` and `xs.index`/`xs.remove` (`ValueError`), `xs.pop` (`IndexError`), `d.pop(k)` without a default (`KeyError`), minus what an enclosing `try`'s handlers catch (a class derived from one they name), plus what its handlers and its `finally` block let escape (D90). The catchable faults (a division by zero, an index out of range, unpacking arity, `del` of a missing index or key) are never in a set: they are implicit in the operators, as a panic is next to a `Result` in Rust, and listing them would put `raises IndexError` on most functions. A call by a name that a `def` shadows counts the builtin too unless that `def` runs before any other code (before every other module statement and parameter default), since a call before the `def` runs reaches the builtin; such a `def` also means no argument is surely a number, as values its calls return are typed by the `def`. A raised value's class comes from the value: a call `ValueError(...)` or a name `ValueError`, an `except ValueError as e` binding (which may hold any class derived from `ValueError`), a module-level name also as the builtin it is until bound, and through variables, conditional expressions and `and`/`or`; anything else (a parameter, a function's result, a list element) is an `Exception`. An escape of a base class may be of any class derived from it, so only a handler of that class or one it derives from removes it: `except ZeroDivisionError` leaves an `ArithmeticError`, and only `except Exception` removes an `Exception`; likewise only a clause naming that class or a base admits it. A clause changes no behavior: removing it, like removing `temper`, leaves a passing program's output unchanged. A clause listing `Exception` admits any exception, so it tells callers nothing; when no escape from the body is of unknown class it draws a warning (B4 follow-up) at `Exception`, naming the clause that says more: the other classes it lists plus what escapes (`raises IndexError, ValueError`), with no repeated class and none a listed one covers, or "remove the `raises` clause" when that is nothing; applying the suggestion always checks clean, so there is no warning when that clause would name a class the module redefines (`def ValueError(): ...`). There is no way to silence it, as it fires only when the clause can narrow (revisit with a second lint). A body that needs it (re-raising a parameter, or calling a function whose own clause is `raises Exception`) draws none, so only the innermost vacuous clause warns.
- Exceptions (phase 4, D6, D7 as superseded): `raise e` raises an exception value; `raise ValueError` means `raise ValueError()`. A `try` runs its first handler whose class the raised exception is an instance of: that class or one derived from it, in Python's hierarchy (B4, see [Builtins](#builtins-phase-2)), so `except Exception` catches any and a later handler a former one covers never runs, as in Python. An exception no handler catches propagates, through calls, as in Python. A tuple handler `except (A, B):` catches an instance of any class in the tuple or derived from one; the parentheses are required, as in Python before 3.14 (`except A, B:` is an error saying so), a trailing comma is allowed, and so is a repeated class. The classes are names written in the handler: an empty tuple, a nested tuple and a variable holding classes are errors (see [Deviations](#deviations-from-python)). `except Name as e` (or `except (A, B) as e`) binds `e` for the handler and unbinds it afterwards, as Python does, so reading `e` after the handler is an unbound-name error. `raise` ends a path like `return` (no fall-through, post-terminator narrowing), and a `try` ends one when its body and every handler do, or when its `finally` block does. A `finally` block runs however its `try` is left: normally, after a handler, on an exception no handler catches (raised again afterwards, the same object), or on `return`, `break` or `continue`; a `return` value is evaluated first. An exception raised in the block replaces the pending one (D88). Besides `raise`, `int(s)` / `float(s)` of a malformed string and the operator faults division by zero, index out of range and unpacking arity raise catchable exceptions; see [Runtime errors](#runtime-errors).

## Types (annotation syntax)

```ebnf
type        = type_atom ['|' 'None'] ;                  # `None | None` is rejected (checked after parsing)
type_atom   = (NAME | 'None') ['[' type (',' type)* ']'] ;
```

Matches Python: `int`, `str`, `list[int]`, `tuple[int, str]`, `dict[str, int]`, `set[int]`, `None`. Variable-length `tuple[int, ...]` is later. Names resolve in the type namespace. `T | None` (Optional) is in phase 2, including nested positions such as `list[int | None]`; general `A | B` unions remain later. Optional is one fixed union type, not permission to change a variable's type. PR #10 implements the token/AST contracts and Optional inference at module level; PR #13 implements this type syntax and `is` / `is not` parsing, including nested annotations. PR #14 implements supported post-terminator narrowing. PR #16 adds Optional fixtures and in-process lex/parse/infer diagnostic checks. PR #17 wires CLI `check`/`run` and validates the current 35-program executable corpus; this is not exhaustive edge-case coverage. `raise` narrows like `return` since phase 4 (B1). See [open implementation work](roadmap.md#phase-2-open-implementation-work).

For example, `x: int | None = None` followed by `x = 5` keeps the same `int | None` type. Nano confirmed that a None-first variable intended to hold a value requires an explicit annotation. Without it, `x = None` fixes the type as `None`, so a later `x = 5` is a type error with a fix-it suggesting `x: int | None = None`. Do not relax loose-mode Optional inference yet; revisit only after the corpus shows how often the annotation is needed.

## Expressions

Lowest to highest precedence:

```ebnf
expr_list   = expr (',' expr)* [','] ;                  # a comma makes a tuple
expr        = 'pause' expr                             # M6c: marks a wait on a task
            | or_expr ['if' or_expr 'else' expr] ;     # conditional expression
or_expr     = and_expr ('or' and_expr)* ;
and_expr    = not_expr ('and' not_expr)* ;
not_expr    = 'not' not_expr | comparison ;
comparison  = sum (comp_op sum)* ;                       # chained, as in Python
comp_op     = '==' | '!=' | '<' | '<=' | '>' | '>=' | 'in' | 'not' 'in'
            | 'is' | 'is' 'not' ;                       # `is` only with a None operand (checked by inference)
sum         = term (('+' | '-') term)* ;
term        = factor (('*' | '/' | '//' | '%') factor)* ;
factor      = ('-' | '+') factor | power ;
power       = postfix ['**' factor] ;
postfix     = atom (call | subscript_op | attr)* ;
call        = '(' [args | expr comp_for] ')' ;            # a bare generator expression only alone (D119)
args        = arg (',' arg)* [','] ;
arg         = [NAME '='] expr ;                          # keyword args by name
subscript_op = '[' (expr | slice) ']' ;
slice       = [expr] ':' [expr] [':' [expr]] ;
attr        = '.' NAME ;
atom        = NAME | INT | FLOAT | STRING
            | 'True' | 'False' | 'None'
            | '(' expr ')'
            | '(' ')'                                    # empty tuple
            | '(' expr ',' [expr (',' expr)* [',']] ')'  # tuple: (a,) (a, b) (a, b,)
            | '[' [expr (',' expr)* [',']] ']'           # list literal
            | '[' expr comp_for ']'                      # list comprehension (D85)
            | '{' [expr ':' expr (',' expr ':' expr)* [',']] '}'   # dict display; `{}` is an empty dict
            | '{' expr ':' expr comp_for '}'             # dict comprehension (D116)
            | '{' expr (',' expr)* [','] '}'            # set display (M6)
            | '{' expr comp_for '}'                      # set comprehension (D116)
            | '(' expr comp_for ')' ;                    # generator expression, a reducer's argument only (D119, D121)
comp_for    = 'for' comp_target 'in' or_expr (comp_for | 'if' or_expr)* ;
comp_target = NAME | comp_target (',' comp_target)+ [','] | '(' comp_target ')' | '[' comp_target ']' ;   # no subscripts (D86)
```

### Semantic rules

- **Slice reads (#1168, D72-D74):** `x[a:b]` and `x[a:b:c]` slice strings, lists and tuples. String/list bounds are integers (bools compute as 0/1); `None` is not accepted as a bound (a listed deviation); omitted bounds use Python's direction-dependent defaults. Bounds clamp to the sequence, negatives count from its end, and a negative step reverses direction. Omitted stop with a negative step differs from an explicit `-1`. The receiver, start, stop and step are evaluated exactly once, left to right; a mutable receiver's length is observed after those evaluations. A zero step, literal or computed, raises catchable `ValueError: slice step cannot be zero` at the slice after its operands execute. This operator fault is untracked in `raises`; operand calls still contribute their declared errors.
- String slices count Unicode code points, including combining marks separately, without normalization. A list slice creates a fresh shallow outer list; selected nested objects remain shared, with the same modes, alias and task rules as `list(xs)`. Tuple slices preserve fixed positional types (D7), selecting their fields with omitted or signed integer literal components, including unary `+`. Computed tuple components, even for homogeneous tuples, are the named error "a tuple slice needs literal bounds". A literal-zero tuple slice never yields a value; it does not acquire a fabricated empty-tuple type. Slice writes (`x[a:b] = v`, `x[a:b] += v`) and `del x[a:b]` remain named unsupported forms; an ordinary target containing a slice read (`xs[:][0] = v`) is allowed.

- List comprehensions (D85): `[elt for t in it ...]` builds a `list[T]` of the element's type, evaluating as the nested `for`/`if` loop it stands for, in CPython's order. Names a comprehension binds belong to it alone, as in Python 3: they do not leak, and an outer variable of the same name (of any type) is untouched; the first iterable is evaluated in the enclosing scope, later clauses and the element see earlier targets. Iterables and filters are `or_expr`, so a conditional or a bare tuple there needs parentheses, as in CPython. A filter narrows like an `if` test (`[x + 1 for x in xs if x is not None]` is `list[int]` for `xs: list[int | None]`) until a later `for` clause rebinds the name; `if x` does not narrow. A `for` clause's iterable is a `for`'s iterable, so `enumerate`/`zip` are accepted there (D51, D58). An element whose type nothing fixes is the "cannot infer" error, as `[]` is. Ownership, aliasing and task checks see the loop.
- Dict and set comprehensions (D116): `{k: v for ...}` builds a `dict[K, V]` and `{e for ...}` a `set[T]`, with a list comprehension's scoping, clauses, narrowing and loop checks (D85). Each pass evaluates the key before the value, as CPython 3.8+ does; a key seen again keeps its first place and takes the later value, as `d[k] = v` does. Keys and elements follow the display rules: one hashable type, so an unhashable key or element is the displays' "unhashable type" error and a `float` key their "not supported yet" error (deviations, Dict keys and set elements).
- Generator expressions (D119-D122): `(e for ...)`, or `f(e for ...)` as a call's only argument, has a list comprehension's scoping, clauses and typing (it is typed as `[e for ...]` would be), and runs as the loop it stands for while its reducer reads it: the first iterable is evaluated once at the call, then the reducer's other arguments (D123), `sum` adds each item as it comes, and `any`/`all` stop at the item that decides, as in CPython; an int `sum` that overflows faults at that item (D2). `sep.join(...)` takes `str` items (D120). Where it may appear is under Deviations.
- `/` is true division (float); `//` is floor division. Same as Python.
- `and`/`or` short-circuit and return an operand, as in Python.
- Comparison chains evaluate each operand once.
- A bare `expr_list` statement is allowed (calls for effect).
- Tuples are fixed-length, immutable values. Subscript assignment on a tuple is an error. Element types are positional, so `(1, "a")` is `tuple[int, str]`.
- Unpacking arity must match. A mismatch is a compile error when both lengths are statically known, otherwise a runtime error.
- Call arguments and list elements are comma lists but never tuples: `f(1, 2)` is two arguments, `f((1, 2))` is one tuple.
- `a, b = b, a` evaluates the right side fully before assigning.
- Lists are homogeneous: every element has one type. `[1, "a"]` is a type error unless the element type is `dyn`. A variable of type `dyn`, the Python-bridge escape hatch, may hold anything; this does not implicitly turn heterogeneous lists or ordinary variables into `dyn`. The bridge remains phase 5; this decision does not claim `dyn` is implemented in phase 2.
- A variable has one fixed type, inferred once (or constrained by its annotation); assignment and augmented assignment cannot change it. See [Decided](#decided) for the no-widening diagnostic and Optional boundary.
- `int ** int` returns `int`. A negative integer exponent is a runtime error, except that a literal negative exponent with an integer base is a compile-time error. Both diagnostics say "use a float base"; `2.0 ** -1` is legal.
- A tuple subscript must be an integer literal, optionally negated (`t[-1]`), so the element type is known statically.
- Subscripts apply to lists, strings, and tuples. A negative index counts from the end: `xs[-1]` is the last element. An index out of range in either direction is a runtime error, except on a tuple: there the index and the length are both static, so it is a compile error, like an unpacking arity mismatch. Slices follow the slice-read rules above (D72-D74).
- Indexing a string and iterating over it (`for ch in s`) yield a length-1 `str`, counted in code points, as in CPython. Under UTF-8, indexing a non-ASCII string is O(n); the phase-3 backend deals with that.
- `in` with a `str` on the right is a substring test. The left operand must be a `str`; anything else is a compile error.
- Lists support `+` and repetition by an int (either operand order); `+=` with another list and `*=` mutate in place, including through aliases. Tuple `+` concatenates positional fields; tuple ordering compares shared fields, then lengths when the shared prefix is equal, including mixed numeric field types. Tuple `*` is not implemented.
- List `==` and `!=` compare element-wise. Both lists must have the same element type, otherwise it is a compile error. Scalar `int == float` stays as in Python.
- An annotation that conflicts with the inferred type is a type error.
- Dicts and sets (M6): `{k: v}` is a `dict[K, V]`, `{a, b}` a `set[T]`, `{}` an empty dict and `set()` an empty set, as in Python. Keys share one type, values another, set elements one, and an empty display takes its types from its uses or its annotation, as `[]` does. A display or comprehension with an expected type takes it, so `d: dict[int, int] = {k: 1 for k in [True]}` holds, as `{True: 1}` does (D117). A dict key or set element must be `int`, `str`, `bool`, `None`, or a tuple or optional of them (see [Deviations](#deviations-from-python)); anything else is a compile error. A `bool` key in a `dict[int, V]`, or element in a `set[int]`, is the int it equals, so `True` and `1` are one entry, as in Python, and a stored one is stored as its int (see [Deviations](#deviations-from-python)); an `int` key in a `dict[bool, V]` is a compile error. `d[k]` reads (a missing key raises a catchable `KeyError` holding the key), `d[k] = v` adds or replaces, and `d[k] += v` does both; a replaced key keeps its place. `k in d` tests the keys, `x in s` the elements; `len`, truth, `==` and `!=` (order-blind) and `for` work on both, and unpacking takes the keys or elements. Both keep insertion order. `d.keys()`, `d.values()` and `d.items()` return views of types `dict_keys[K]`, `dict_values[V]` and `dict_items[K, V]` (not spellable in annotations); a view supports `for`, `in`, `len`, truth, `list()` and `sorted()`, and prints as in Python (`dict_keys(['a'])`); it is not subscriptable, comparable or mutable. A `for` loop over a dict or set whose size changes stops the program with a `RuntimeError` (a fault); assigning to an existing key inside the loop is legal (tempered code is stricter; see [Deviations](#deviations-from-python)). Like lists, dicts and sets are mutable heap values (D2): `mut` and `owned` apply.

## Builtins (phase 2)

A closed set. Anything else is a name error.

- Functions: `print len list set sorted range str int float bool open abs ord chr sum min max any all enumerate zip` (`open` as [Imports](#notes) lists, M6a and #1171). `abs ord chr sum min max any all` follow D56 and D57: `sum min max any all` take what `for` iterates. `enumerate zip` follow D51 and D58: consumed directly, stepped lazily. `list(xs)` takes exactly one list, dict, set, dict view or task-map result iterator (also a directly consumed `enumerate`/`zip`) and returns a new list of what it iterates over; of a list, a shallow copy of the same type (phase 4, D3/D4; M6). `set()` is an empty set and `set(xs)` a new set of what `xs` iterates over. `sorted(xs)` is a new list of what `xs` iterates over, in ascending order by `<`, stable; `reverse=` as `list.sort`; `key=` is "not supported yet" (D51, D70).
- Exceptions (phase 4, D6, B4): the classes `Exception ArithmeticError OverflowError ZeroDivisionError LookupError IndexError KeyError OSError FileNotFoundError PermissionError IsADirectoryError NotADirectoryError RuntimeError RecursionError ValueError`, in Python's hierarchy: `Exception` is the base of all; `ArithmeticError` of `OverflowError` and `ZeroDivisionError`; `LookupError` of `IndexError` and `KeyError` (M6); `OSError` of `FileNotFoundError`, `PermissionError`, `IsADirectoryError` and `NotADirectoryError` (M6a); `RuntimeError` of `RecursionError`; `ValueError` derives from `Exception` directly. Calling one with zero or one argument of any type builds an exception value of that class; `str(e)` and `print(e)` give the argument as a string, empty without one, except that a `KeyError` gives its argument's `repr` (`'k'`), as in Python.
- Methods: `str.split` (`s.split()` on CPython's whitespace, or `s.split(sep)`), `str.join` (of a `list[str]`), `str.strip`, `str.lstrip` and `str.rstrip` (spaces, or the code points of `chars`), `str.replace(old, new)`, `str.startswith` and `str.endswith` (a `bool`), `str.find`, `str.rfind`, `str.index`, `str.rindex` (a code-point index; `find` gives -1 where `index` raises) and `str.count` (an `int`), and `str.upper` and `str.lower` (full Unicode case mapping), each as CPython computes it (D49, D53; see [deviations](#deviations-from-python)); `list.append`, `list.extend` (of what `for` iterates), `list.insert(i, x)` (an index past either end clamps, as in CPython), `list.pop()` / `list.pop(i)`, `list.remove(x)`, `list.index(x)` and `list.count(x)` (an `int`), and `list.sort()` (in place, ordered as `sorted`; `reverse=` allowed) (D70); `set.add`; `dict.get` (`d.get(k)` is `V | None`, `d.get(k, default)` is `V`), `dict.pop(k)` / `dict.pop(k, default)` (`default` of the value type), `dict.setdefault(k[, default])` (no `default` means `None`), `dict.update(other)` (a dict of the same type) (D70), `dict.keys`, `dict.values`, `dict.items`, each returning a view (M6); a file's `read` and `close` (M6a).
- Type names: `int float str bool list tuple dict set None Exception bytes`. `Exception` is the one type of every exception value, so `except ValueError as e` and `except IndexError as e` can share `e`; the class of a value is known when it runs, as in Python, not from its type.

## Runtime errors

A fatal fault (overflow, recursion depth, out-of-memory, `0.0 ** -1`, ...) means a bug: `try` never catches it. It stops the program, prints a diagnostic with its source span to stderr, and exits with status 1, as an uncaught CPython exception does.

These raise catchable exceptions, with CPython's messages: `raise`; `int(s)` / `float(s)` of a malformed string (a `ValueError`); `/`, `//` and `%` by zero, int or float (a `ZeroDivisionError`); a list, string or range index out of range, read, store or `del` (an `IndexError`); a dict read or `del` of a missing key (a `KeyError`, M6); a failed `os.listdir`, `os.path.getsize`, `open`, file read, write, `flush` or writer `close` (an `OSError`, as the subclass the error names, M6a, D96); invalid UTF-8 read as text (a `UnicodeDecodeError`, D93); using a closed file (a `ValueError` with CPython's per-type message, M6a, D96); `s.split(sep)` with an empty `sep` (a `ValueError`, D53); `s.index(sub)` or `s.rindex(sub)` of a missing `sub` (a `ValueError`, D50); `chr(n)` out of range or of a surrogate, and `min`/`max` of an empty iterable (a `ValueError`, D50/D56); `xs.pop()` of an empty list or `xs.pop(i)` out of range (an `IndexError`, D71); `xs.remove(x)` or `xs.index(x)` of a missing `x` (a `ValueError`, D71); `d.pop(k)` of a missing key with no default (a `KeyError`, D71); a slice with a zero step (`ValueError: slice step cannot be zero`, untracked); and unpacking a list, string or range of the wrong length (a `ValueError`). One no handler catches ends the program the same way, with CPython's last traceback line as the message (`ValueError: bad`, or just `ValueError` when the message is empty) and the span of its `raise`, call or operator: the diagnostic a fault gives. `int` of a NaN float or of a numeric string outside `i64` stays a fault.

A compile error (lexical, syntax, or type) is reported before anything runs: `pythrust run` prints the diagnostic to stderr, writes nothing to stdout, and exits with status 1.

A warning (a lint) is a note on a valid program. `run`, `check` and `build` print each to stderr as `path:line:col: warning: ...`, with the line and a caret underline, in source order, once every check passes and before anything runs; warnings never change the exit status or the program's output. A built executable prints none.

## Manifest (`pythrust.toml`)

Decided for M6d (Nano, 2026-11-03; [research/package-tool.md](research/package-tool.md)); implemented in M6d's manifest PR (#97). A project's manifest is a strict subset of TOML 1.0. Every form the subset accepts parses to the same values under CPython 3.13's `tomllib`, which an oracle test checks. Any other form, valid TOML or not, is a named error at its line and column.

```ebnf
manifest = { line } ;
line     = ws [ header | pair ] ws [ comment ] newline ;
header   = '[' ws bare ws ']' ;
pair     = bare ws '=' ws ( string | inline ) ;
inline   = '{' ws [ ipair { ws ',' ws ipair } ] ws '}' ;  (* no trailing comma *)
ipair    = bare ws '=' ws string ;                        (* values inside an inline table are strings *)
string   = '"' { char | escape } '"' ;                    (* one line *)
escape   = '\' ( '"' | '\' | 'b' | 't' | 'n' | 'f' | 'r' | 'u' HEX*4 | 'U' HEX*8 ) ;
bare     = ( ALPHA | DIGIT | '_' | '-' ) { ALPHA | DIGIT | '_' | '-' } ;
ws       = { ' ' | '\t' } ;
comment  = '#' { any character but a control character other than tab } ;
newline  = '\n' | '\r\n' ;                                (* the last line may omit it *)
```

- `ALPHA`, `DIGIT` and `HEX` are ASCII only (`A-Z a-z`, `0-9`, `0-9 A-F a-f`).
- A control character is U+0000 to U+001F or U+007F, as in TOML 1.0. Other characters, U+0085 included, are allowed in strings and comments.
- A `char` is any character except `"`, `\` and a control character other than tab. A `\u` or `\U` escape must name a Unicode scalar value.
- The file is UTF-8. Invalid UTF-8, a byte-order mark and a carriage return not followed by a line feed are each a named error.
- **Each of these is a named error** that says what to write instead:
  - literal (`'...'`) and multi-line strings;
  - quoted and dotted keys, and dotted table headers (`[a.b]`);
  - arrays and arrays of tables;
  - integers, floats, booleans and dates;
  - an inline table inside an inline table.
- **Keys:**
  - A table or key defined twice is an error.
  - A key outside the schema is an error, and so is a key before the first table.
- **Schema:**
  - `[package]` is required, with `name` and `version`, both strings. `name` is ASCII letters, digits, `-` and `_`, starting with a letter.
  - `[rust]` maps a binding name to `{ path = "..." }`. A binding's name is a plain name that is no CPython 3.13 standard module (any of `sys.stdlib_module_names`, implemented here or not, since a standard module always wins an import; D128), builtin or keyword.
  - `[python]` and `[pythrust]` are reserved: present at all, each is an error.
  - A `[rust]` path is relative to the manifest's directory, `/`-separated (a `\` is the error "write `/`"), and never absolute; `..` may climb out of the project.
- **Discovery** (Nano, 2026-11-03): every program looks for a manifest, whose directory is the root its local modules are found in (D75), but only one with a module importing a local module (D125) or a name neither standard nor local (D81) reads it. The search starts in the program's directory as its path is written, made absolute, with each `..` taking off the name before it as text; symlinks are not resolved, so `link/../x` is `x` beside `link`. It goes up to the filesystem root and stops at the first `pythrust.toml`. `check` and `build` print `pythrust: using <path>` to stderr when they use one, and every manifest error names it. A binding is checked (its directory and stub) only when a program imports it.

## Deviations from Python

This is the canonical documented deviations-from-CPython list. Thread E treats these as expected differences, not bugs, and links deviation fixtures here. The [Decided](#decided) section supplies rationale; other docs should reference this list rather than maintain another one.

- **`...` (M6b, Nano 2026-10-31):** a function body of `...` is legal only in a Rust binding's stub; elsewhere a statement `...` is a named error ("stub bodies only; use pass"), where CPython accepts it. `...` as a value (Python's `Ellipsis`, as in `x = ...`) is not supported either, an error with no fix-it. A deliberate omission, to revisit when Protocol or trait support lands.
- **`OSError` from a Rust binding (M6b):** an `io::Error` maps to the four known subclasses (`FileNotFoundError`, `PermissionError`, `IsADirectoryError`, `NotADirectoryError`); any other becomes a plain `OSError` where CPython raises a further subclass such as `FileExistsError`, and its `str` lacks the file name.
- **Rust bindings (M6b) are a Pythrust extension:** CPython cannot import one, so such a program has no CPython oracle; its tests compare it with a pure-Pythrust program doing the same work ([research/rust-interop.md](research/rust-interop.md#oracle)).
- **Compiler nesting guard:** recursive grammar nesting and expression tree height are each limited to 100. A leaf has height 1; a compound expression adds 1 to its deepest child. Flat left-associative chains and postfix chains count too: a standalone 100-term addition is accepted, while 101 terms report `too deeply nested`. Wrapping an expression (for example in a call or list) also counts; parentheses alone do not add a tree node. Width alone (list elements or chained comparison operands) does not add height. The parser checks each constructed node, keeping partial trees at most 101 high on rejection, so later recursive passes and cleanup cannot inherit an unbounded tree. Evaluation remains left-associative and in source order; this compiler resource bound is separate from the runtime call limit. Process regressions: `tests/expression_limits.rs`; accepted near-limit order controls: `flat_expression_order`, `flat_expression_overflow`.
- Spaces only: a tab outside a string or comment is an error, not just in indentation.
- An unknown string escape (`'\q'`) is an error; CPython keeps the backslash and warns.
- `\N{name}` escapes are not supported.
- Strings hold Unicode scalar values: a surrogate escape (`'\uD800'`) is an error.
- String prefixes and triple quotes are rejected with a dedicated error.
- `NAME` is ASCII only.
- **Checked overflow:** ints are `i64`; overflow is a runtime error, including `i64::MIN // -1`, `-i64::MIN`, `abs(i64::MIN)` and `2 ** 64`. An out-of-range literal is a compile error (with the unary-minus boundary exception specified above).
- **Fixed variable types:** a variable cannot be rebound to a different type. Flow-sensitive type-changing rebinding is outside the current subset; `dyn` is the explicit Python-bridge escape hatch.
- **No int-to-float variable widening:** `total = 0` followed by `total += 1.5` is a compile error, with a fix-it to initialize with `0.0`. Mixed arithmetic within an expression still promotes as in Python; the variable's type does not widen.
- **Negative integer exponents:** `int ** int` returns `int`; a negative exponent is a runtime error. With an integer base, a literal negative exponent (`x ** -1`) is a compile-time error. Both messages say "use a float base". `2.0 ** -1` stays legal.
- Lists are homogeneous; tuple subscripts are integer literals, optionally negated. So are dicts (one key type, one value type) and sets.
- **Dict keys and set elements (M6, Nano 2026-10-31):** must be `int`, `str`, `bool`, `None`, or a tuple or optional of them. A `list`, `dict`, `set` or view key is a compile error, "unhashable type", where CPython raises a `TypeError` at runtime. A `float` key, or a tuple holding one, is a compile error, "not supported yet", where CPython accepts it; floats wait for a reason to settle NaN and `-0.0` keys. Fixtures `dict_key_float`, `dict_key_unhashable` and, for a comprehension (D116), `setcomp_unhashable`.
- **Bool keys in int-keyed dicts and sets (M6, Nano 2026-10-31):** a `bool` stored as a key of a `dict[int, V]` or an element of a `set[int]` is stored as its int, so `d: dict[int, str] = {True: 'a'}` then `d[1] = 'b'` prints `{1: 'b'}`. CPython keeps the first key object stored and prints `{True: 'b'}`. Lookups agree. Fixture `dict_bool_key`. `run` is the reference. It does not specialize generic code, so it marks a table int-keyed only where code with a concrete type makes it, stores to it, passes it or receives it, or when the table first stores an int. A generic function that makes a table, stores a bool in it and shows it before returning it to such code shows `True` in `run`. `build` would show `1`, so instead it refuses any bool stored as a key of an int-keyed dict or set inside a generic function, a named backend gap (Nano, 2026-10-31; fixture `dict_bool_key_generic`, [roadmap](roadmap.md#phase-5-m6-plan)).
- **Set order (M6):** a set iterates and prints in insertion order, as a dict does. CPython's set order follows hashes, so it differs for most sets and changes between runs for strings. Fixture `set_order`.
- **Dict views (M6, Nano 2026-10-31):** a view is a snapshot taken when `keys()`, `values()` or `items()` is called, so a view held across a change to its dict does not see the change. CPython's views are live. A view used where it is made (`for k in d.keys():`, `list(d.items())`, or an argument of `enumerate` or `zip` such as `for i, v in enumerate(d.values()):`) behaves the same in both: a `for` over a view it makes, directly or through `enumerate`/`zip`, reads the dict itself, so it sees a value updated in the body, and growing the dict inside it fails as above (D60). Only a view bound to a name is a snapshot. Fixtures `dict_views` and `zip_sources`.
- **Changing size during iteration (M6):** a `for` loop over a dict or set that grows stops the program with CPython's `RuntimeError` message, but as a fault: `try` does not catch it. In tempered code it is a compile error instead (D4), whose fix-it for a named, flat container replaces the iterable with `list(d)` and says it costs a copy; as for a list, any store into the container inside the loop counts, a store at an existing key included, since the check does not track which keys exist.
- **Imports (M6a):** `import` must come before a module's other statements, and a module exposes only the names Pythrust supports; a late import or an unsupported name (`sys.platform`) is a compile error. A module is not a value (`m = sys`), and `sys.argv = [...]` is a compile error, "not supported yet". Fixtures `import_late` and `module_name_unsupported`.
- **Modules (post-M6 step 3, #1220; the `from` and `as` forms planned in #1222):** a circular import is a compile error, where CPython runs the cycle with a partially initialized module (D75). A local module named like any CPython stdlib module, or like a `[rust]` binding, is a named error, where CPython lets the first on `sys.path` win (D75, D81). An `__init__.pyr` ("packages with `__init__.pyr` are not supported yet") and relative imports (`from . import x`) are errors (D78); so is `from a import *` ("`import *` is not supported; import the names you use", D79) and assigning another module's global (`a.X = 1`, "not supported yet", D83). A local module is not a value, as a stdlib module is not. A module file beside a directory of its name is an error, where CPython imports the file (D78). Fixtures `examples/modules/` `import_cycle`, `import_main`, `stdlib_shadow`, `package_init` and `module_beside_dir`.
- **`sys.argv` (M6a):** a built program's `sys.argv[0]` is the path it was started by, where CPython's is the script's path; `pythrust run` gives the file's path as CPython does. An argument that is not UTF-8 is decoded lossily (U+FFFD), where CPython keeps its bytes as surrogate escapes.
- **`os` (M6a):** `os.path.join` follows POSIX rules (`/`) on every platform, where CPython on Windows uses `ntpath` (`\`, drives). On Windows an `OSError`'s message and `repr` carry the system's error code and text after `[Errno N]`, where CPython maps the code to a C errno, writes `[WinError N]` and uses its own wording; the class agrees. A directory entry name that is not UTF-8 is decoded lossily. A path holding a NUL character raises an `OSError` from `os.listdir` and `os.path.getsize`, where CPython raises `ValueError`; `open` raises CPython's `ValueError`. Fixtures `os_path` and `os_error_uncaught` catch by class only, so they agree on every platform.
- **Files (#1171, D91-D100):** the file's type carries its kind, text reader, text writer, binary reader or binary writer (D99), so reading a file opened for writing is the compile error "file opened for writing is not readable" (and "file opened for reading is not writable"), where CPython raises `io.UnsupportedOperation` at run time (fixtures `file_not_readable`, `file_not_writable`); a reader and a writer cannot share a variable, the ordinary type-change error, where CPython rebinds (`file_reader_writer_rebind`). Modes other than the nine literals (`"x"`, `"+"`, reordered spellings such as `"br"`) are "mode '<m>' of `open` is not supported yet", and a computed mode is "`mode` of `open` must be a string literal" (`open_mode_unsupported`). Text is UTF-8 whatever the platform's locale: `encoding=` takes only the UTF-8 spellings `utf-8`/`utf8` (any case, `-` or `_`) or `None`, so CPython's aliases `"u8"` and `"cp65001"` and other encodings are errors, as are `newline=`, `errors=`, `buffering=`, `closefd=` and `opener=` (`open_encoding_unsupported`); plain CPython on Windows reads its locale code page (the oracle runs `-X utf8`). Constructing a `UnicodeDecodeError` is "not supported yet" (`unicode_decode_construct`; CPython takes five arguments). Only `for` and `list(...)` read a file's lines; `sorted(f)`, `set(f)`, `x in f`, `enumerate(f)`, `zip`, `min`, `max`, `any`, `all`, `sum`, `extend` and comprehensions of a file are "only `for` and `list(...)` read a file's lines yet; use `list(f)`" (`file_lines_consumer`, D100). `with` takes `open(...)` directly: a file already open (`with g as f:`) is "`with` takes `open(...)` directly; a file already open is not supported yet", where CPython accepts any file (`with_file_already_open`, D109), and Python 3.10's parenthesized items (`with (open(a) as f, open(b) as g):`) are "parenthesized `with` items are not supported yet" (`with_parenthesized_items`, D113); a parenthesized value alone (`with (open(p)) as f:`) is accepted. Writes are buffered, so another handle may see less of a file still open for writing than under CPython, whose buffer sizes differ; a write error in the implicit flush at a drop or the program's exit is dropped silently, where CPython prints an "Exception ignored" note (D98).
- **String methods, str A (D53):** `sep.join(x)` takes a `list[str]` only; a set, dict view, `str` or tuple of strings, or a dict with `str` keys, is a compile error, "not supported yet; use `list(...)`", where CPython accepts any iterable of `str` (a dict yields its keys). `split` with a literal `""` separator is a compile error, where CPython raises `ValueError: empty separator` at runtime; a computed empty separator raises that `ValueError`. `maxsplit`, `sep=`, `replace`'s `count`, `strip`'s `chars=` keyword and a `None` separator or `chars` are compile errors, "not supported yet". Fixtures `str_join_not_list`, `str_split_empty_sep` and `str_method_arg_unsupported`.
- **List and dict methods (D70):** `list.index`'s `start` and `end` arguments, `key=` of `list.sort` and `sorted`, `dict.update` of key-value pairs, keyword arguments or no argument, and `del` of a name, of several targets or of an attribute or slice are compile errors ("not supported yet"), where CPython accepts them. Fixtures `list_method_arg_unsupported`, `sort_key_unsupported`, `dict_update_unsupported`, `del_form_unsupported`, `list_method_nan`.
- **Slicing (D72-D74):** `None` or `int | None` slice bounds are a type error ("slice bounds must be integers"); slicing a `range` (or any receiver other than a string, list or tuple) is "slicing <type> is not supported yet"; a tuple slice with a computed part is "a tuple slice needs literal bounds"; slice assignment (`xs[a:b] = ...`, `xs[a:b] += ...`) and `del` of a slice are "not supported yet". CPython accepts all of these. Fixtures `slice_receiver_range`, `slice_receiver_dict`, `slice_tuple_computed`, `slice_tuple_homogeneous`, `slice_assignment`, `slice_aug_assignment`, `slice_delete`; `slice_bound_none`.
- **String methods, str B (D55):** the `start` and `end` arguments of `startswith`, `endswith`, `find`, `rfind`, `index`, `rindex` and `count` are compile errors ("`start` of `str.find` is not supported yet"), and so is a tuple of prefixes or suffixes for `startswith` and `endswith` ("`str.startswith` of a tuple is not supported yet"), where CPython accepts them. Fixture `str_search_arg_unsupported`.
- **Unicode version of case mapping (D49, D55):** `upper` and `lower` follow the Rust standard library's Unicode tables, which may be newer than CPython 3.13's Unicode 15.1; a code point given a case mapping since then maps where CPython leaves it (`'ɤ'.upper()` is `'Ɤ'`, U+A7CB, where CPython gives `'ɤ'`). Fixture `str_case_unicode_version`.
- **`repr` of a string (post-M6 step 1):** `repr`, and so `print` of a list, tuple or dict holding strings, escapes control characters, separators other than space (U+00A0, U+3000) and private-use characters as CPython does, but prints format characters (Cf, such as U+200B, U+00AD and U+FEFF) and unassigned code points raw, where CPython escapes them (`'\u200b'`). Fixture `str_repr_unprintable`.
- **Builtins, PR 4a (D56, D57):** `ord` of a computed string whose length is not 1 stops the program with CPython's message (`TypeError: ord() expected a character, but string of length 2 found`) as a fault: `try` does not catch it, and `TypeError` is not a class here; a literal such argument is a compile error. `ord` of `bytes` is "not supported yet". `chr` of a surrogate (U+D800–U+DFFF) raises `ValueError: chr() arg is a surrogate, which a str cannot hold`, where CPython returns a lone surrogate (a literal one is a compile error, as a surrogate escape is). `min`/`max` of mixed `int`, `float` and `bool` arguments or elements is a compile error, where CPython returns whichever object wins. `sum`'s `start` must have the result's type (`sum(floats, 0)` is an error with fix-it `0.0`), and `sum` of lists or tuples is "not supported yet", where CPython accepts both. An empty `sum` of floats with no `start` is `0.0` (D50), where CPython gives the int `0`. In a generic function, which `run` does not specialize, such a sum is the int `0` under `run`, as in CPython; `build` would give `0.0`, so instead it refuses a `sum` of floats with no `start` inside a generic function, a named backend gap (fixture `builtin_sum_empty_float_generic`). Fixtures `builtin_ord_length`, `builtin_chr_surrogate`, `builtin_minmax_mixed`, `builtin_sum_start`, `builtin_sum_empty_float` and `builtin_sum_empty_float_generic`.
- **Iterators are not values (D51, D58):** `enumerate(...)` and `zip(...)` are accepted only as a `for`'s iterable, as the argument of `list sorted set sum min max any all` or `str.join`, or nested directly in each other. Anywhere else, for example `e = enumerate(xs)` or a return, the compile error is "`enumerate(...)` is not a value yet; use `list(enumerate(...))`". `zip(strict=)` is "not supported yet". Iteration is lazy, in CPython order. Suggested fixtures `enumerate_not_value`, `zip_not_value`, plus an oracle fixture for `enumerate(zip(...))`.
- **Generator expressions are reducers' arguments only (D119-D123):** `(e for ...)` is accepted only as the iterable of `sum` or `sorted`, the one argument of `list set min max any all`, or the argument of `sep.join`; written bare it must be a call's only argument, as in CPython. Anywhere else, for example `g = (x for x in xs)`, a user function's argument or a `for`'s iterable, the compile error is "a generator expression is not a value yet; use a list comprehension `[...]`" (fixture `genexp_not_value`). Beside one, `sum`'s `start` and `sorted`'s `reverse=` must be a literal or a name: anything else is "a computed `start` of `sum` with a generator expression is not supported yet" (fixture `genexp_computed_start`). Lifted by step 7-4 (#1281).
- An out-of-range tuple index (`(1, 2)[2]`) is a compile error, so nothing runs. Python raises an `IndexError` at that point.
- Type errors are reported before the program runs, so a program with one prints nothing. Python raises the same mistakes as a `TypeError` at runtime, if it raises them at all.
- `1 in "abc"`: a non-`str` left operand of `in` on a string is a compile error. Python raises a `TypeError`.
- **NaN in containers (Nano):** list and tuple `==`, `!=`, ordering and `in`, and `list.index`, `list.count` and `list.remove`, use value equality only, with no identity shortcut, so a NaN never equals itself inside a list, tuple or dict value: for `x = float('nan')`, `[x] == [x]`, `(x,) == (x,)` and `x in [x]` are all `False`. CPython checks identity first and returns `True`; it agrees with Pythrust only when the NaNs are different objects.
- `list(x)` copies a list, dict, set, dict view or `map`'s results, and consumes a direct `enumerate`/`zip` call: `list("ab")`, `list(range(3))`, a tuple, or no argument is a compile error. Python accepts any iterable and `list()` returns `[]`.
- List equality needs the same element type: `[1] == [1.0]` is a type error, where Python compares element-wise and returns `True`.
- `==` and `!=` between types that can never be equal (`1 == "a"`) are type errors; `int`, `float` and `bool` compare freely.
- Functions are not values yet: a `def` name may only be called. A name cannot be both a `def` and a variable, and a `def` name is defined once.
- A function that returns a value on some path must not fall off its end (that returns `None`) unless its return annotation is `T | None`.
- `is` / `is not` compare only with `None`. In an `if`/`elif`/`while` whose test is `x is not None`, and in the clauses after an `x is None` test, a `T | None` name `x` has type `T`, unless that block assigns `x`. An `if x is None:` whose body always leaves (`return`, `raise`, `break`, `continue`, also from a loop's `else` when that loop has no `break`), or an `if x is not None:` whose `else` always leaves, also narrows `x` for the rest of the enclosing block, unless the other side or the rest assigns `x`. An `if` with `elif` clauses does not. Tests compose with `and`, `or` and `not`: `a and b` holding proves what either side proves when holding, and failing proves only what both sides prove when failing; `or` is the mirror image, and `not` swaps holding and failing. So `if x is None or k > x:` narrows `x` in later clauses and `if x is None or y is None: return` narrows both. The same applies inside expressions: the right side of `a and b` sees what `a` holding proves, the right side of `a or b` what `a` failing proves, and `t if c else f` narrows `t` and `f` by `c` holding and failing. Truthiness (`if x:`) does not narrow, because `0` and `""` are false too; an error on such a name in the body suggests `x is not None` (Nano). CPython runs these programs.
- A variable first bound to `None` has type `None` unless annotated: `x = None` then `x = 5` is a type error; write `x: int | None = None`. `T` and `None` flow into `T | None` (also inside tuples); lists stay invariant, but a list, tuple, dict or set display, or a comprehension, takes its element (key, value) types from where it goes (an annotation, argument, return or reassignment), so `xs: list[int | None] = [None, 1]` and `ys: list[int | None] = [x for x in xs if x is not None]` hold (D117).
- A negative `float` raised to a fractional power is a runtime error; Python returns a `complex`, which the subset lacks.
- Mixed `int`/`float` arithmetic and comparison, and `int / int`, go through `f64`, so results can differ from Python's exact math for magnitudes above 2**53.
- **`finally` (D88, D89):** a fatal fault stops the program without running `finally` blocks, where CPython's exception runs them (fixture `try_finally_fault`). `return`, `break` or `continue` leaving a `finally` block is a parse error ("`return` inside `finally` is not supported"); CPython 3.13 accepts it, discarding a pending exception or overriding a pending `return`, and 3.14 warns (PEP 765). A `break` or `continue` of a loop wholly inside the block is legal. Fixtures `try_finally_return`, `try_finally_break`, `try_finally_continue`.
- **Some faults are fatal (D7 as superseded):** overflow, recursion depth and out-of-memory are never caught, though `OverflowError`, `RecursionError` and `MemoryError` are exceptions in Python; `except ArithmeticError` catches `1 // 0` but not an overflow. So are `0.0 ** -1` (a `ZeroDivisionError`) and the other `**` errors, and `int` of a NaN or of a numeric string outside `i64`. Division by zero, an index out of range and unpacking arity are caught as in Python (fixtures `fault_caught`, `fault_caught_by_exception`).
- Bare `except:` is not supported yet (D6): it is a parse error whose fix-it is `except Exception:`, which catches any. Fixture `except_catch_all`.
- **Tuple handlers take literal names only (Nano, 2026-10-29, #56):** `except ()`, which catches nothing in Python, is a parse error (fixture `except_empty_tuple`); a nested tuple `except ((A, B), C):` is a parse error saying to list every class in one tuple; exception classes are not values, so `errs = (ValueError, IndexError)` and `except errs:` are errors saying classes can't be held in variables. Unparenthesized `except A, B:` is an error as in CPython 3.13, the oracle; 3.14 accepts it without `as` (PEP 758), which stays out for now (fixture `except_tuple_unparenthesized`).
- **Pause (M6c, Nano 2026-11-02):** CPython has no `pause`; it runs a program with the markers removed. So tempered code missing a marker (fixture `tasks_tempered`) and a marker covering nothing that waits (`tasks_pause_empty`) are compile errors where CPython runs the program.
- **Tasks (M6c, Nano 2026-11-01):** the locality rules above reject programs CPython runs: an executor at module level (fixture `tasks_module_level`), a future returned (`tasks_future_returned`), in a global (`tasks_future_global`) or a tuple (`tasks_future_tuple`), `map`'s results used after the block (`tasks_results_outside`), a builtin passed to `submit` or `map` (`tasks_submit_builtin`), an executor bound by assignment or opened by a `with` on an existing one, a `with` over a program's own `open`, whatever it returns (D115, `with_user_open`), a use of a name that a binding from another `with` block may reach, even on a path that never runs, and a program using tasks that lowering cannot otherwise express (`tasks_lowering_gap`). Rule 4 rejects programs CPython runs: two tasks sharing a list one changes (`tasks_share_list`), the submitter changing a list inside one a task reads (`tasks_reach`) or a result sharing a task's argument (`tasks_result_alias`), two tasks of a function appending to its list default (`tasks_default_list`) or to a module list (`tasks_module_list`), a nested executor's task against the outer block's (`tasks_nested`), `map` with a function that changes its parameter (`tasks_map_changes`), and a file passed to a task (`tasks_file`); its analysis is coarser than the program's runs, as a `submit` in a loop shares whatever its arguments may share across iterations. An executor used after its block is a compile error where CPython raises a `RuntimeError` (`tasks_executor_after_block`). `ThreadPoolExecutor` takes no arguments: `max_workers`, by keyword or position, is a compile error where CPython sizes its pool by it (`tasks_max_workers`); the pool is always `min(32, cpus + 4)` threads. `run` runs each task at `submit`, so: output a task prints may interleave with other output differently than under CPython's threads; natively, a task's unfinished line (`print(x, end="")`) reaches stdout when the line ends or the task does, so it may come out after output CPython would print later (fixture `tasks_partial_line`), and one unfinished line of 64 KiB or more is published in pieces, which may interleave with another such line from another task (`tasks_long_line`; whole lines never mix; Nano, 2026-11-01 and 2026-11-02); a task that starts an executor when the system will start no further thread ends the program, where CPython's threads may still run it (test `a_refused_thread_ends_the_program`, Linux) (each executor starts at most `min(32, cpus + 4)` threads, with 8 MiB stacks); a `for` over `map`'s results left early (`break`, `return`, an exception raised in the loop body, or one a task raised, taken as its result), and likewise `in` stopping at a match or `list`, `sorted` or `set` stopped by a task's exception, does not cancel the tasks that have not started, as CPython does, and leaving the `with` waits for all of them (Nano, 2026-11-01; fixture `tasks_map_break`); and tasks nested inside tasks more than about 7,000 calls deep in all stop the program ("tasks nest too deeply to run at submit"), where CPython's threads each have their own stack. A fatal fault in a task stops the program, as anywhere (D7), where CPython keeps a `RecursionError` or `OverflowError` for `result()`; natively it does so when the task runs, at no fixed point relative to what the submitter prints meanwhile. So natively, how much output other threads print before the stop is nondeterministic; `run`, which runs each task at `submit`, is deterministic (Nano, 2026-11-02). A catchable exception escaping a task whose result is never taken is dropped, as in CPython.
- **Parameter modes (D2):** a tempered function whose body needs a `mut` or `owned` it does not write, or any function whose written mode its body outgrows, is a compile error, so nothing runs; so is a mode its type cannot have (`owned n: int`, `mut s: str`). - **Shared arguments to a tempered function (A5):** a call that may pass one list, or a list inside it, to two parameters of a tempered function, one of them `mut` or `owned`, is a compile error about the call, in loose code too; the fix-it is a copy, `list(...)`. CPython runs the program with the modes removed. Fixtures `modes_shared_call` and `modes_shared_forward`.
- **Aliasing in tempered bodies (D3, D4):** a tempered body that changes a list through one name while another name for the same list is still used later, that changes a list a `for` loop is running over, or that returns a parameter or a value sharing a list with one, is a compile error, so nothing runs. - **Lowering gaps in tempered programs (Nano, 2026-11-03):** a program containing a `temper def` that lowering cannot yet express is a compile error naming the gap, so its ownership checks are never skipped silently; CPython runs it (fixture `temper_lowering_gap`).
- **Declared errors (D8):** a tempered function that lets an exception escape without listing it in a `raises` clause, or any function whose clause misses one, is a compile error, so nothing runs. CPython runs the program with the clause removed. Fixtures `raises_undeclared` and `raises_late_shadow`.
- **Comprehension targets (D86):** a comprehension target is a name or a tuple of names; a subscript target (`[0 for xs[0] in ys]`), legal in CPython, is the parse error "a comprehension target other than a name or a tuple of names is not supported yet". Fixture `listcomp_subscript_target`.

### Observed implementation limitations (#805)

These verified differences record current implementation behavior, not newly approved permanent language deviations. Choosing to retain or fix them is outside this documentation update; existing recorded decisions still govern. Reproduce each snippet saved as `probe.pyr` with CPython 3.13 (`python3.13 probe.pyr`), `pythrust check probe.pyr`, `pythrust run probe.pyr`, and `pythrust build probe.pyr` followed by `./probe` (`probe.exe` on Windows). Native builds need the [runtime setup](native.md#runtime-resolution).

**Unicode numeric conversion:** string `int`/`float` conversions reject non-ASCII decimal digits with a catchable `ValueError`, where CPython accepts them. This is a runtime conversion difference: `check` and `build` accept the program, and the built executable matches `run`. The interpreter (`interp/builtins.rs`) and runtime (`pythrust-rt/src/num.rs`) trim with Rust `str::trim`, require ASCII digits for `int` and underscore separators, and use Rust float parsing. This does not imply ASCII-only strings or string methods. Verified controls: ASCII digits and surrounding U+00A0 are accepted by both; U+001C surrounding digits is rejected by both numeric converters (despite CPython `str.strip` removing it).

```python
for s in ["١٢", "１２", "١_٢", "１２.５"]:
    try:
        print("int", int(s))
    except ValueError:
        print("int ValueError")
    try:
        print("float", float(s))
    except ValueError:
        print("float ValueError")
```

Pythrust prints `int ValueError` then `float ValueError` for each input (exit 0). CPython prints `int 12` / `float 12.0` for the first three and `int ValueError` / `float 12.5` for the last. An uncaught conversion failure exits 1 with a `ValueError` diagnostic; this is not a compile-time rejection of Unicode text.

**List augmented assignment:** a tuple or range on the right of list `+=` is rejected by inference, before execution, even if all elements match the list's element type. `check`, `run` and `build` exit 1 with `unsupported operand types for +: list[int] and tuple[int, int]` (or `... and range`), no stdout and no new executable. CPython extends the list in place and prints `[1, 2, 3]` (exit 0):

```python
xs = [1]
xs += (2, 3)  # In a separate probe, replace with: xs += range(2, 4)
print(xs)
```

A list RHS (`xs += [2, 3]`) works in all three paths and preserves aliases, as does list `*=`; corpus `list_arith` checks those controls. `infer/stmt.rs::aug_assign` uses the binary operand constraint; the interpreter's broader internal iterable operation is not CLI acceptance. Do not suggest `list(range(...))` or `list(tuple_value)` as a fix: those constructors are themselves unsupported (see the existing `list(x)` deviation above).

- **Slice subset (#1168):** recorded in the main list (D72-D74); fixture index as before: `slice_tuple_computed`, `slice_tuple_homogeneous`, `slice_tuple`, `slice_assignment`, `slice_aug_assignment`, `slice_delete`, `slice_list`, `slice_receiver_range`, `slice_receiver_dict`, `slice_bound_float`, `slice_step_float`, `slice_bound_generic_invalid`, `slice_bound_generic`, `slice_bound_generic_tuple`, `slice_alias_return`, `slice_alias_mutation`, `slice_tasks_alias`, `slice_tempered`, `slice_tasks`, `slice_pause`, `slice_pause_unmarked`, `slice_bound_none`.

## Deliberate omissions (phase 2)

`from` imports, `import a.b`, `import a as b`, keyword arguments to module functions other than `os.listdir(path=...)`, an `OSError`'s `errno`, `strerror`, `filename` and `args`, generator expressions outside a reducer's argument (D121), set operators (`|`, `&`, `-`, `^`, `<=`), removing entries (`discard`, set `remove`, `clear`, `popitem`, `del` other than one subscript), list `copy`/`reverse`, `dict(...)` and `frozenset` (M6 adds them as programs need them), slice assignment/deletion, computed tuple slice components and `None` slice bounds, starred unpacking (`a, *b = ...`), multi-index subscripts (`a[1, 2]`), lambda, classes, `try` `else`, bare `raise`, exception chaining and user-defined exceptions, `with` on a value other than an executor or a direct `open(...)` call (user context managers, step 5), file lines read by anything but `for` and `list(...)` (D100), `open` modes past the nine listed, encodings other than UTF-8 and `open` keywords other than `mode=` and `encoding=`, file methods past `read()`, `readline()`, `write`, `flush` and `close` (`read(n)`, `readlines`, `writelines`, `seek`, `tell`, `truncate`, attributes), `readline` and lines of a binary file, `print(..., file=f)`, hash objects as values (`update`, `digest`, other algorithms), `bytes` literals and operations past `len`/`==`/`!=`, decorators, bitwise operators, chained assignment (`a = b = 1`), bare declarations (`x: int` with no value), `tuple[int, ...]`, general `A | B` unions (except phase-2 `T | None`). Each is additive: existing phase-2 programs keep their meaning.

## Decided

- **Integers:** `i64` with checked overflow (runtime error, no silent wrap).
- **Fixed variable types (Nano):** one type per variable, inferred once; no rebinding to a different type. `total = 0` followed by `total += 1.5` is a compile error with a fix-it: "total is int here; write 0.0". Do not widen the variable from int to float: if the loop never runs, that changes the output from `0` to `0.0`, violating "tempering never changes meaning". Flow-sensitive type-changing rebinding such as `x = int(x)` is out of scope now; ship a clear error, then use the conformance corpus to decide whether to revisit it. A same-type assignment is unaffected.
- **Optional (Nano):** pull `T | None` into phase 2 so None-initialized values can be represented without arbitrary type-changing rebinding. Optional remains one fixed union type. **None-first annotation confirmed by Nano:** write `x: int | None = None` when a None-first variable must later hold an int; unannotated `x = None` then `x = 5` is an error with that fix-it. Do not relax loose-mode Optional inference yet; revisit after corpus evidence shows how often the annotation is needed.
- **Optional follow-ups (Nano, in order):** parser support for `'|' 'None'` and `is` / `is not`; then a separate PR for narrowing after a terminating `if x is None` branch (`return`, `break`, `continue`), with each implemented terminator tested and a fall-through negative case; then Optional conformance cases once parsing lands. These narrow an existing fixed union, not the variable's declared type. **Raise deferral confirmed by Nano:** implement and test `return`/`break`/`continue` narrowing now; defer the `raise` test until `raise` exists. `raise` arrived in phase 4 (B1) and narrows like `return`, with its test.
- **Lists and dyn (Nano):** homogeneous element types; `[1, "a"]` is an error unless the element type is `dyn`. A `dyn` variable may hold anything. `dyn` is the explicit Python-bridge escape hatch, not an implicit fallback.
- **Integer powers (Nano):** `int ** int` returns `int`; negative exponents fail at runtime. A literal negative exponent with an integer base fails at compile time. Both diagnostics say "use a float base". `2.0 ** -1` remains legal. Checked overflow already makes `2 ** 64` a runtime error.
- **Tempering marker:** `temper def f(...)`, a keyword prefix.
- **Tuples:** Python syntax. Fixed-length, immutable, positionally typed. Unpacking in assignment and `for`. **Tuple bounds confirmed by Nano (#12):** an out-of-range tuple index is a compile error because index and length are static, so nothing runs; list/string out-of-range indexes remain runtime errors.
- **Source file extension:** `.pyr`.

- **Pause marker** (M6c, implemented): `pause <expr>`, a loosely binding prefix covering the whole expression to its right, like Swift's `await`. Required in tempered code at every pause point; it must cover at least one. See [research/concurrency-syntax.md](research/concurrency-syntax.md).
- **Shared lock** (lands with concurrency): a builtin type `shared[T]`, built with `shared(v)` and accessed through `with x as n:`, where `n` writes through. Not a keyword.

- **Tasks** (M6c, Nano 2026-11-01): a subset of `concurrent.futures.ThreadPoolExecutor` scoped by `with`; from `submit` to the end of the executor's `with` block, no two parties (the submitter and each task) may touch one container, or anything it reaches, where either changes or keeps it, in loose code too; `run` runs each task at `submit`; only waits on other tasks are pause points. See [research/concurrency.md](research/concurrency.md). Implemented for the scoped subset described above; `shared[T]` and channels remain parked.

`shared` stays reserved until it lands, so adopting it breaks no programs; `with` and `pause` became keywords with M6c. `temper` is already live in `func_def`.

### Phase 4 (M5): tempering, ownership, exceptions (Nano, 2026-10-27)

Implemented within the recorded scope below; [roadmap.md](roadmap.md#phase-4-m5-plan) orders the work. Ownership direction and vocabulary are in [research/ownership.md](research/ownership.md).

- **D1, what tempering requires:** a `temper def` annotates every parameter and its return, uses no `dyn` in its signature or body, and writes the `mut`/`owned` modes its body needs (D2), including `owned` on a string it keeps or returns (A8). Implemented (A1) for annotations: each must be complete, so `xs: list` is an error, and a missing one suggests the inferred type when it can be spelled, such as `n: int`. The `dyn` rule holds trivially until `dyn` lands, since no code may use it yet. Modes implemented (A4); see the notes above.
- **D2, ownership modes:** a contextual prefix on a parameter, `def grow(mut xs: list[int])`, `def keep(owned xs: list[int])`. `read` is the default and is never written. `mut` and `owned` are not reserved, so `mut = 1` stays legal. Loose functions may write modes; the compiler checks them against the body. Implemented (A4). Only a tempered callee's `mut` makes passing one list twice an error (ownership.md, decided 2); loose-to-loose calls keep Python aliasing. Extended to every heap type (Nano, 2026-10-29, A8): `owned` on any heap type, required when the body keeps the parameter, `mut` only when the type's operations reach a list, neither on a value type; see the parameter-modes note above. D3 and D4 stay list-only: a tempered function may return a string parameter (it is `owned`, no copy fix-it), and `b = a` on strings is no aliasing error. Why: one rule for what tempering writes down, keyed on what the type is rather than on its refcount representation, so a kept string is as visible in a signature as a kept list.
- **D3, returned aliases:** tempered code may not return an alias of a parameter (`return xs`); for a flat list the fix-it copies the value being returned (`return list(xs)` for `return xs`). A shallow copy still shares nested lists, dicts or sets, so no shallow-copy fix is offered when the returned type can retain them, or when `list(...)` would change its type. Loose code may, tracked by the inferred summary. A new builtin `list(xs)` makes a shallow copy. Implemented (A6): a value that holds a parameter or a list inside one counts, as does a list the body stored in a parameter.
- **D4, aliased mutation:** in tempered code, two live names for one list with a mutation through either (`b = a`, then `b.append(1)` while `a` is used) is an error; for a standalone append of a simple value to a named flat-list receiver the fix-it copies its current value immediately before the change (`b = list(b)`). Optional or computed receivers, nested containers and other unproved rewrites get prose guidance instead of fabricated code. Diagnostics name the actual list, dict or set and distinguish a running loop reference from an ordinary live temporary. A mapped input counts as running only during its own target binding or body, not while its iterable is evaluated or its else runs; an active outer loop still counts during nested iterable evaluation. There is no share marker in phase 4. Loose code keeps Python's aliasing. Implemented (A6), non-lexically: only a name used after the change counts. A list inside another is its own list, so `r = rows[0]` then `r.append(1)` while `rows` is used is legal, but two names for `rows[0]` are two names for one list, and so are any two names of one type reached inside a value the body did not build (`pair[0]` and `pair[1][0]` of a `tuple[list[int], list[list[int]]]` may be `(xs, [xs])`). A parameter may be a global's list (`f(saved)`), so it may share lists with the globals of its types; two parameters share none, which A5 checks at the call. A module variable the body, or a function it calls, reads after the change counts as a name used later, and a call to a function that changes a module variable's list, itself or through its callees, is a change at the call. A `mut` argument is a change to the list and every list inside it. Changing a list a `for` loop is running over is the same error, with the fix-it `for x in list(xs)`. A computed receiver (`a if c else b`, `a or b`, `a and b`) counts through each possible source separately: choosing `b` must still check a later use of an alias `a`. Independent receivers and a repeated single source remain legal. Passing one list twice to a call is A5's check.
- **D5, tempered calling loose:** a tempered function calls only tempered functions and builtins; otherwise the error says "temper `f` first". Implemented (A1), defaults included. The crossing annotation in [design.md](design.md#core-idea-tempering) waits for module tempering or the Python bridge.
- **D6, exception surface:** builtin exception names only: `ValueError`, `IndexError`, `ZeroDivisionError`, `OverflowError`, `RecursionError`; B4 adds their bases (below). `raise ValueError("msg")`; `try:` with one or more `except Name [as e]:` or `except (A, B) [as e]:` clauses (`as` is allowed only there until `with` lands); `str(e)` and `print(e)` give the message. Bare `except:`, `else`, `finally`, chaining and user-defined exceptions are later; their words stay reserved.
- **D7, what can be caught:** faults that mean a bug stay fatal as today: overflow, index out of range, division by zero, unpacking arity, recursion depth. Only `raise` and the parse builtins `int(s)` / `float(s)` (which raise `ValueError`) can be caught. A deviation from Python: `except IndexError` around `xs[10]` never catches. **Superseded (Nano, 2026-10-30, #59; implemented):** division by zero (int and float `/`, `//`, `%`, a `ZeroDivisionError`), index out of range (list, string and range reads, list stores, an `IndexError`) and unpacking arity (a list or string of unknown length, a `ValueError`) become catchable at `except` sites; overflow, recursion depth and out-of-memory stay fatal. Implicit operator faults are never tracked in `raises` (an explicit `raise` and `int(s)` / `float(s)` stay tracked), nor is reading a closed file (a `ValueError`, as in CPython; Nano, 2026-10-31, M6a); a handler for one is never reported unreachable; the `raises Exception` lint ignores them; an uncaught one still prints `run`'s diagnostic and exits 1. See [research/faults.md](research/faults.md). `**` stays fatal, `0.0 ** -1` included, since the decision lists `/`, `//` and `%` only.
- **D8, declared errors:** a tempered function lists the errors that escape it with a contextual `raises` clause after the return type, `temper def parse(s: str) -> int raises ValueError:`. Loose functions infer theirs. Explicit `Result[T, E]` types and a `?` operator are later.
- **B4 choices (Nano, 2026-10-29, confirmed on #55):** (1) The bases `Exception`, `ArithmeticError`, `LookupError` and `RuntimeError` are classes like the others: `except`, `raises` and `raise` take them, and `Exception("msg")` builds one, as in Python. (2) A handler catches its class and the classes derived from it; one an earlier handler covers is legal and never runs, as in Python (no error). (3) A `raises` class admits the classes derived from it, and an escape of a base class (an `except ArithmeticError as e` binding re-raised) is not removed by a handler of a subclass. (4) Faults stay fatal under every handler, `except Exception` included (D7). (5) Bare `except:`, `BaseException` and the classes no builtin raises (`KeyError`, `TypeError`, ...) stay out; bare `except:` suggests `except Exception:`. Tuple handlers were left out here and came in their own PR (B4 follow-up, #56; Nano confirmed its four choices 2026-10-29: parentheses required, `(A,)`/`(A)`/trailing comma legal with `()` an error, a repeated class legal, literal names only). `raises Exception` stays legal though it makes a declared set vacuous; a warning says so when the body does not need it (B4 follow-up, #57; Nano confirmed 2026-10-30: a warning, not an error; only when the clause can narrow, with no silencer until a second lint; the suggestion keeps the other listed classes; no warning flags yet). Revisit D7 once lowering exceptions to `Result` makes faults cheap to catch, since `except Exception` around `1 / 0` is the most visible deviation.
- **A6 choices (Nano, 2026-10-28):** four rules A6 implements, confirmed by Nano in the project thread (2026-10-28 22:05 UTC) after #48 merged, and on #49. (1) A list inside another is its own list: `r = rows[0]; r.append(1)` while `rows` is used is legal, as `for r in rows: r[0] = 0` is. (2) The caller is not a name: `ys = xs; ys.append(1)` with `xs` unused afterwards is legal, since `mut xs` already shows the caller the change. (3) Changing a list a `for` loop is running over is a D4 error, fix-it `for x in list(xs)`. (4) A list held in an exception (`raise ValueError(xs)`) is kept past the call, like one stored in a global, so the parameter needs `owned`. A copy avoids that only when it holds no list of the parameter: `ValueError(list(xs))` for `xs: list[int]` needs no mode, but for `xs: list[list[int]]` the shallow copy still holds `xs`'s inner lists, so `owned` is still required.
